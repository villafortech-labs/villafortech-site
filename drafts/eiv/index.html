01 / THE PROBLEM

Correct logic is only
part of the contract.

Before a system can verify an action, someone has to decide what the instruction means. If the intended meaning never enters the set of interpretations, every subsequent check can agree on the wrong answer.

EIV makes the proposed action explicit: the operation, resource, recipient, scope, and relevant facts. It then compares candidate permission policies and records the clarification steps behind a simulated allow, deny, or abstain decision.

The intended application is a conversational agent with an inspectable permission layer. The implemented artifact is a local research workbench, CLI, and Python core; general chat and real tool enforcement remain separate integration work.

    READ THE DENOMINATORS

    V3 contains 1,440 constructed cases and 28,800 outcome records across policies, question orders, and budgets. The 288-row comparisons above are specific slices. These repeats are correlated; six scenarios share one Boolean structure. Cases are AI-authored and lack independent human semantic review.

    Additional findings preserved in the repository
    Study Observation What it establishes
    V2 · 40 cases Both methods: 28 correct. EIV: 25 vs 40 questions, with 4 additional false allows and 4 additional false denials. Less questioning can be a negative tradeoff.
    Local model pilot · 10 cases 7 correct; one candidate per case; zero questions. Structured generation feasibility, without testing targeted clarification.
    Selection counterexample · 8 intents One-question budget: targeted resolves 0/8; first resolves 1/8. Neither makes an incorrect decision. Pair-separation score is not generally budget-optimal.
    V0.4 exact planner · post hoc On the known counterexample, resolves 1/8 at budget one versus greedy 0/8; at larger budgets, avoids fruitless follow-up questions. A bounded engineering correction to a known failure. Missing-interpretation failures remain.
    V0.4 / ENGINEERING VALIDATION

    Release v0.4.0 passed 194 automated tests on each Python version from 3.10 through 3.14, including HTTP integration. The planner is checked against a separate reference on 564 small policy problems. Its post-hoc experiment records 17,280 outcomes over inspected cases; it is separate from the frozen V3 evidence and is not prospective validation.

    04 / BUILT TO BE EXAMINED

    A small core.
    An explicit boundary.

    Python, finite models, strict structured inputs, and replayable decisions. The scientific replay and local workbench need no third-party runtime dependencies.

    01

    Represent

    Controlled English or strict JSON specifies the domain, action, resource, recipient, scope, facts, candidate meanings, and questions.

    eiv/permissions.py
    02

    Check

    The finite evaluator checks each interpretation. Contradictions, unknown conditions, and resource limits can lead to abstention.

    eiv/logic.py
    03

    Plan

    Compare first, greedy, or exact bounded questioning. The v0.4 planner maximizes resolved supplied hypotheses, then minimizes total questions.

    eiv/planning.py
    04

    Replay

    The API revalidates posted sessions and recomputes decisions. Export candidate checks, answer IDs, restrictions, and a final reason in JSON.

    eiv/web.py
    ∴

    Consensus is conditional. An allow decision depends on faithful interpretations, adequate coverage, correct facts, and the declared finite semantics. EIV does not execute tools, enforce real permissions, or prove that human intent is covered.

    05 / AN EXPLICIT ACTION RECORD

    Trace the decision
    back to its inputs.

    The export records public inputs and computed checks. It exposes what the system represented and how a reply changed the candidate set. It is not a transcript of a model's private reasoning.

    What a reviewer can inspect in the current workbench
    Record Concrete content Boundary
    Requested action For example: messages / send / report / Alex / once, alongside the original instruction and supplied facts. An explicit proposed operation, not proof that the representation matches intent.
    Candidate checks Candidate IDs, matching permission dimensions, condition values, formal status, and allow/deny/abstain reasons. All checks remain conditional on the supplied policies and facts.
    Clarification history The selected question, answer ID, and candidate IDs before and after restriction. Answers filter existing meanings; they cannot silently expand permission or repair omitted meanings.
    Final result Decision, reason, active candidates, question counts, and explicit simulated/unverified-coverage flags. A replayable research result, not a signed capability or execution receipt.

    FROM WORKBENCH TO AGENT

    Implemented: finite permission reasoning, three question strategies, local interaction, strict replay, and exported evidence. Future integration: a general chat adapter, authenticated approvals, tool enforcement, revocation, and execution receipts. Those require a separate security design and evaluation; a workbench allow decision is not authorization to execute a real action.
